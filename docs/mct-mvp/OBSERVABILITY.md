# MCT 过程记录与可视化 MVP

当前状态：RFC #2 Phase 0 已完成，Phase 1 已有单 agent Fabric 观察客户端垂直切片。启用 `MCT_TELEMETRY=1` 后，真实 agent 的 Pathfinder、位置采样、决策、动作和对话事件会进入统一的版本化 JSONL；观察客户端能在普通 Minecraft 1.20.1 世界中叠加实际轨迹与白色连续计划路径，并提供单角色状态、目标标记和 owo-ui 事件检查器。run_id 切换自动清空旧记录。三 agent 场景和完整暂停屏障尚未实现。脚本 agent 演示仍用于 recorder 和控制流程验收。

观测主画面改为 Minecraft 内的空间展示：外部页面和 JSONL 负责完整记录与控制，Minecraft 负责让观察者在现场看到轨迹、决策浮字和当前状态。此前的二维页面只作为 recorder 的调试视图，不是最终展示。

## 目标

让观察者能够回答四个问题：

1. 三个角色实际走过了什么路线，在哪里停留、分开、重聚或死亡？
2. 某个关键时刻角色看到了什么状态，收到了谁的消息？
3. 它生成了什么可见决定，解析成了什么命令，命令实际执行结果如何？
4. 暂停时是否真的停止了世界和三个角色，恢复后是否接着同一次运行继续？

旁观画面只作为现场证据，不能代替这四类记录。

## 当前代码能提供什么

MindServer 当前约每秒请求一次每个 agent 的完整状态，并发送给网页。状态包括位置、生命、食物、维度、生物群系、世界时间、背包、附近实体和当前活动。页面还接收角色输出和聊天消息。

Mindcraft 的 prompt/response 日志目前是分散的文本文件。它们没有和状态采样、动作执行、其他角色消息共用运行编号，也没有形成可点击的时间线。因此它们可以作为原始材料，不能直接作为可视化记录。

## 首版记录格式

每次试跑生成一个 `runId`，在 `run/evidence/<runId>/` 下保存：

- `run.json`：场景、版本、种子、A/B、角色、开始/结束/暂停区间和最终状态。
- `events.jsonl`：追加写入的事件，事件不覆盖，便于中途查看和事后复盘。

事件统一包含以下字段：

```json
{
  "runId": "2026-10-28T12-00-00Z-abc",
  "seq": 42,
  "wallTime": "2026-10-28T12:15:03.120Z",
  "gameTick": 18342,
  "agent": "MCT_A",
  "type": "decision",
  "decisionId": "d-17",
  "data": {}
}
```

首版事件只保留实际有用的几类：

| 类型 | 记录内容 |
| --- | --- |
| `state` | 位置、维度、生命、食物/饱和度、背包摘要、当前活动、世界时间 |
| `message` | 发送者、接收者、消息内容、是否触发回应 |
| `decision` | 触发消息或事件、当时的结构化状态、模型可见输出、解析出的命令 |
| `action` | 命令/动作开始、结束、成功、失败、超时或被暂停；关联 `decisionId` |
| `world` | 入夜、天亮、受伤、死亡、复活、拾取/消耗食物、进入/离开目标区域 |
| `run` | 开始、暂停请求、暂停确认、恢复请求、恢复完成、结束 |

`state` 每秒采样一次；位置移动超过一个方块时额外采样。这样可以画出连续轨迹，又不会按每个游戏 tick 无限增长日志。关键事件必须立即写入。

“决策记录”只记录可观察的输入、生成文本、命令和结果，不声称获得模型不可验证的内部思维。是否保存完整 prompt 作为本地原始日志，可以通过配置开关决定；默认展示结构化状态和模型输出。

## 早期外部页面草案（已由 RFC #2 的游戏内观察端取代）

首版页面只有三个区域：

1. **轨迹区**：以 A 为原点的二维俯视图，三人使用不同颜色的折线；B、营地、死亡点、食物事件和决策点作为标记。点击某个点跳到对应时间线位置。
2. **时间线区**：按 MCT_A、MCT_B、MCT_C 和世界分泳道排列事件；可以只看消息、决定、动作、食物或危险事件。暂停时可以拖动查看已经发生的记录。
3. **详情区**：显示选中事件前后的状态差异、触发来源、模型输出、解析命令和动作结果，并链接到对应轨迹点。

顶部显示运行状态和控制：`运行中 → 暂停中 → 已暂停 → 恢复中 → 运行中`。暂停和恢复是运行控制，不是删除或重启角色。

## 早期命令演示（历史实现）

脚本 agent 演示使用一个管理员观察者 Mineflayer 连接向专用普通世界发送原版命令：

- 以三种颜色的 concrete 方块和同色 dust 粒子绘制轨迹；
- 以 `text_display` 在当前位置显示角色名、生命、食物和当前动作；
- 在决策地点生成带“决定”和“命令”的浮动文字；
- 用 `tellraw` 和 actionbar 显示消息、日落、天亮、进食和暂停/恢复；
- 所有显示实体带 `mct_demo` 标签，退出时集中清理。

这属于早期演示，曾留下测试方块。当前展示由只读 Fabric 客户端叠加完成，不再向世界放置轨迹方块或显示实体；具体操作见 `client/observatory/README.md`。

## 暂停与恢复边界

首版只支持同一次运行内暂停，不支持关闭程序后的恢复。

暂停流程必须有明确的屏障：

1. 运行控制器先写入 `run.pause_requested`，阻止新的模型请求进入。
2. 三个 agent 在 prompt、消息和动作边界检查暂停标记；正在执行的动作被安全中断并记录为 `interrupted`，模型已经发出的请求可以返回，但结果只能缓存，不能执行。
3. 每个 agent 清除移动、挖掘、战斗和寻路控制，并确认 `agent.paused`。
4. 普通 MC 服务端进入冻结状态，并确认世界时间、实体、生存消耗和玩家物理不再推进；旁观者仍可移动观察。
5. 三个 agent 和服务端都确认后才写入 `run.paused`，页面才显示“已暂停”。

恢复时按相反顺序解除屏障，重新读取三人的真实状态，再继续目标。被中断的路径或动作可以重算；暂停前已经收到的消息按记录顺序继续处理。暂停区间不计入有效运行时长。

原版 `/tick freeze` 不能直接作为完整方案：它的版本和玩家冻结语义需要与机器人连接方式一起验证。普通世界可以使用支持冻结的版本或轻量服务端适配器；这与 Tellus 无关。

## 实现顺序

1. 先做 recorder：不接模型，验证 `state`、轨迹、世界事件和 `events.jsonl` 可持续写入。
2. 在 prompt、命令解析、动作管理器和聊天转发处加入 `decisionId/actionId`，形成“输入 → 决定 → 命令 → 结果”链。
3. 用 Fabric 观察客户端完成单 agent 的实际轨迹与计划路径叠加；保留 JSONL 作为完整记录。
4. 单 Agent 的 owo-ui 事件详情完成后，再扩展到三 agent 的消息与事件关联，加入整体暂停屏障；先用短场景验证暂停/恢复，再进入跨夜旅行。

## 首版验收

- 选择任意一个时间点，可以同时看到三人的位置、状态、消息、当前动作和最近一次决策。
- 从一条决策可以跳到它触发的动作、动作结果和轨迹位置。
- 轨迹能显示分开、重聚、停留、死亡/复活和抵达 B。
- 暂停后世界时间、食物、实体和三个 agent 的动作都不继续变化；恢复后同一 `runId` 继续记录。
- 关闭并重新启动后的恢复明确显示为“不支持”，不伪装成首版能力。
